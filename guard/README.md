# sbb-guard — сторож решений

Отдельный процесс (и, на стенде, отдельный пользователь ОС), который **единственный говорит «загружать»**: хранит одобрения, окна доверия, секрет второго фактора (TOTP) и журнал решений с цепочкой хешей. Дизайн — `secure-bb-guard-design.md` (вариант B). Ядро bb (патч 0003, не здесь) перед загрузкой не встроенного плагина спрашивает сторожа по Unix-сокету; плагин `secure-bb` в режиме «сторож» спрашивает его же и только **добавляет** ограничения.

Ноль зависимостей: только `node:*`. Исходник читаемый, **без сборки**: Node (≥ 22.18) сам снимает типы TypeScript, поэтому то, что прочитано, то и выполняется. Ставится root-ом (установщик — отдельная задача), код root-owned.

```
sbb-guard serve          [--data DIR] [--socket PATH] [--socket-gid GID]
sbb-guard totp-register  [--data DIR] [--code CODE] [--replacing-code CODE]
sbb-guard status         [--data DIR] [--socket PATH]
sbb-guard journal-verify [--data DIR]
sbb-guard import FILE    [--data DIR] [--yes] [--digest SHA256]
```

Пути — из аргументов или окружения, не из кода: `--data` / `SBB_GUARD_DATA` (по умолчанию `/var/sbb-guard`), `--socket` / `SBB_GUARD_SOCKET` (по умолчанию `/var/run/sbb-guard/guard.sock` — **вне** каталога данных), `--socket-gid` / `SBB_GUARD_SOCKET_GID` (группа сокета: в ней должен быть только пользователь bb). Для тестов — временный каталог.

## Что где лежит

| Путь | Что | Права |
|---|---|---|
| `<data>/state/` | закрытый каталог сторожа | 0700 |
| `state/guard.db` | SQLite (`node:sqlite`): одобрения, очередь, окна, попытки ввода кода, журнал | 0600 |
| `state/totp.secret` | секрет TOTP. Пишет **только** `totp-register`; ни один запрос сокета его не возвращает | 0600 |
| `state/journal.head` | голова журнала (`id hash`) отдельным файлом | 0600 |
| `state/alive` | метка жизни (pid, время), раз в 5 с | 0600 |
| `/var/run/sbb-guard/` | каталог сокета (вне данных) | 0750, владелец `_bbguard`, группа — та, где только пользователь bb |
| `/var/run/sbb-guard/guard.sock` | сокет | 0660, владелец `_bbguard`, группа та же (`--socket-gid`) |

Данные (`<data>`, `state/`) остаются `0700` и недоступны пользователю bb; сокет лежит в своём каталоге **`0750 _bbguard:<группа bb>`**, сам сокет — `0660`. Сторож создаёт каталог сокета с `0750`, если его нет; владельца и группу ставит установщик (или `--socket-gid`). Нужны права не `0700` на корень данных: путь к сокету через него не идёт.

## Почему SQLite (`node:sqlite`), а не файл

Одобрение, запись очереди и запись журнала должны меняться **вместе или никак**: оборванная перезапись JSON-файла теряет или рвёт их. SQLite даёт это одной транзакцией (WAL, `synchronous = FULL`), а данных мало. `node:sqlite` встроен в Node — нативного модуля и зависимости нет (`better-sqlite3` плагина сюда не нужен). Цена: Node ≥ 22.18; на 22.x модуль помечен как экспериментальный.

## Протокол

Построчный JSON: одна строка запроса → одна строка ответа, на одном соединении можно подряд. Таймаут запроса 5 с, строка не длиннее 512 КБ, не более 64 соединений. Ответ `{"ok":true,…}` или `{"ok":false,"error":{"code","message"}}`; `id` запроса возвращается в ответе. Коды: `invalid`, `not_found`, `conflict`, `not_registered`, `invalid_code`, `blocked`, `unknown_op`, `internal`.

**Без кода** (может прислать любой процесс пользователя bb, в том числе вредный плагин — поэтому они ничего не разрешают сверх решённого человеком):

| op | что |
|---|---|
| `decide {pluginId, version, contentHash, rootDir, source, sourceKind, trigger}` | хеш одобрен → `proceed`; открыто окно на `pluginId` → `proceed` + одобрение «окном» в журнале; иначе → `wait` и запись в очередь |
| `state` | очередь, одобрения, окна, журнал (для страницы); секретов нет |
| `annotate {requestId \| contentHash, findings}` | проверки плагина к записи очереди; **только для показа**, помечено «не проверено сторожем» |
| `close-window {windowId \| pluginId}`, `revoke {approvalId \| pluginId}`, `dismiss {requestId}` | ужесточение, без кода и вне блокировки; `dismiss` — только для удержанных записей, в журнал пишется |
| `ping`, `journal-verify` | жив ли; проверка цепочки |
| `lookup {pluginId, contentHash}` | *(дополнение к документу)* только чтение: одобрено ли, открыто ли окно, чьё одобрение. Нужно хуку плагина |
| `hold {…как decide…, stop}` | *(дополнение)* удержать версию для человека; с `stop` окно её не снимает. Ужесточение: хуку плагина нужно «стоп по новой возможности» в окне, а ядро после «держать» хука может сторожа не спрашивать |

**С касанием** (код TOTP): `approve {requestId, code}`, `open-window {pluginId, minutes, code}`, `policy {patch, code}` (расширить — с кодом, сузить — без), `touch {purpose, code}` *(дополнение: проверка кода для действий самого плагина — сторож конфигурации, скиллы, настройки; сторож при этом ничего не решает)*.

Сторож сам проверяет код, **лимит попыток** (5 неверных за час → все касания блокируются на час, в том числе верный код), **повтор шага запрещён** (шаг ≤ последнего использованного не принимается) и пишет журнал. Код тратится только на запрос, который может удаться (не найден / уже решён — отказ без траты).

## Журнал

Цепочка хешей (каждая запись несёт хеш предыдущей) + голова в `state/journal.head`. `journal-verify` (она же выполняется при старте сторожа, на странице и по `journal-verify` через сокет) находит: изменённую запись, удалённую/вставленную/переставленную, обрезанный хвост, откат базы к старой копии (файл головы «впереди»), пропавший файл головы, одобрение, записанное в базу мимо журнала. Код выхода `journal-verify`: 0 — цела, 2 — нарушена. **Это свидетельство, а не замок:** кто может писать и базу, и файл головы (сам сторож, root), перепишет цепочку целиком; замок — что файлы принадлежат пользователю, которым bb не запускается. Старт и остановка пишутся в журнал, перерыв метки жизни дольше 30 с — тоже.

## Регистрация TOTP — только с консоли

`sudo sbb-guard totp-register` рисует QR в терминале (тот же кодировщик, что и в плагине; тест сверяет), показывает ключ один раз, просит первый код и только после верного кода записывает секрет. Секрет **никогда не проходит через bb** — это закрывает перехват регистрации. Заменить секрет можно, только подтвердив его текущим кодом. Хранится файлом `0600` в закрытом каталоге; значения не пишутся ни в журнал, ни в ответы.

## Перенос из плагина: `sbb-guard import FILE`

Плагин по кнопке (с кодом) выгружает свои действующие одобрения в `<данные плагина>/exports/approvals-<время>.json` (формат `secure-bb-approvals/1`) и показывает sha256 файла. Файл делает код внутри bb, поэтому сторож **не верит ему**: `import` печатает каждую строку, сверяет `--digest`, если задан, и спрашивает подтверждение (`--yes` — без вопроса, для скриптов). Каждое принятое одобрение пишется в журнал (`approved.import`), уже одобренные пропускаются, окна не переносятся.

## Чего сторож не решает

- Вредный плагин в процессе bb по-прежнему читает данные bb и секреты других плагинов и подделывает интерфейс — это изоляция плагинов в ядре (вариант C).
- **Код, введённый на странице, идёт через процесс bb.** Вредный плагин может перехватить его и потратить первым на своё действие (код одноразовый, на одно). Поэтому в журнале сторожа записано, *что именно* одобрено, а решение — passkey (подпись над хешем действия), следующий шаг. Тест `KNOWN LIMIT` в `test/guard/malicious-plugin.test.ts` показывает это прямо.
- **Любой процесс пользователя bb может сжечь лимит попыток** (5 неверных кодов → блок одобрений на час). Это цена лимита; закрывать и отзывать при этом можно, блок их не касается.
- Права на сокет — единственный контроль доступа: Node не читает uid собеседника.
